# Evidence-led UI design（v0.1，待专业审阅）

设计与审查从用户要做的事出发，不预设视觉风格。避免将 AI 的判断当作已验证事实。根据任务大小裁剪流程，不为完整性而制造工作。

## 1. 调查实际条件

优先读取已有产品要求、界面、代码、组件库、使用反馈和平台限制。明确：
- **用户与场景**：什么人在什么设备、环境中使用，具备什么知识，受到什么限制。
- **主要任务**：用户要完成的具体操作，以及能观察到的成功条件。
- **关键状态**：开始、进行中、成功、部分成功、失败、中断、恢复。按实际风险选取，不机械枚举。
- **现有约束**：组件、术语、导航、布局与平台惯例。有证据表明需要改变时再改变。

区分 `已观察`、`推论`、`未知`。不得编造研究数据或用户引语。仅在缺失信息会改变关键设计时提问；否则说明最小假设并推进。

## 2. 定义当前最重要的问题

用一两句话说明用户当前的主要困难。区分信息架构、交互路径、系统反馈、无障碍、视觉语言等不同问题，优先处理影响任务完成的因素。

不要把“看起来常见”直接判作 UX 差，也不要把“视觉新奇”直接判作设计好。成熟交互模式可能有助于用户识别。

## 3. 调查并比较设计参考

关键决策不明确时，选取少量与任务相似的真实产品、交互流程或成熟模式作为参考。对每个参考说明：
- 借鉴的是哪项结构、交互或视觉决策。
- 为什么适用于当前用户。
- 哪里不适用，以及参考的来源。

不把截图当成可用性证明，不直接复制无关品牌风格。只有存在实质设计取舍时才生成多个结构方案，并比较任务路径、信息密度、学习成本及实现代价，而不是只换颜色。

## 4. 明确方案，按需实现

新界面或较大改版先明确任务流程、主要信息、重要状态，然后选择视觉表达。重点设计决策（层级、文案、位置、排版、间距、颜色、动效）需能说明对用户任务的作用。

优先复用现有组件及设计约束。不提前发明大量设计系统结构。**如果用户只要求研究、评审或规划，不实现或修改产品代码。**

实际实现时，使用真实内容或具有代表性的样例数据；根据任务处理加载、空白、错误、长内容等状态。只有正常状态的漂亮页面不代表完整交互。

## 5. 观察实际界面并验证

有可运行产品时，应当查看实际渲染与操作，而不是仅检查 JSX/CSS。根据任务检查主流程、反馈、恢复能力、键盘焦点、适用的窗口尺寸和关键异常路径。

对审查结论明确标记：
- **已验证故障**：附复现步骤、截图、测量或测试结果。
- **设计风险**：根据启发式或专业判断提出的问题，尚未由目标用户确认。
- **偏好/候选方案**：主观建议或待研究选择。

不得根据外观声称通过无障碍标准，不得根据 AI 自评分声称 UX 改善。评估方法见 [02-evaluation.md](references/02-evaluation.md)。

## 6. 形成反馈，保留经确认的决策

输出精简报告：用户任务、实际观察、关键设计决定、依据、改动建议、未解决问题和验证状态。优先解决阻断或误导用户的实际问题，不自动扩大到无关的美化。

若是持续维护的项目，把**已经确认**的视觉规范、交互约束与研究发现写回项目已有的设计文档（例如 `DESIGN.md`、`UX.md`）；不要建立重复的事实来源。未经审阅的偏好只能作为候选规则。

## 边界

- 不强制统一风格，不无条件禁用常用字体、卡片或动效。
- 不编造用户画像、竞品界面、用户测试或设计成功数据。
- 不把启发式当强制技术规范，不用 AI 自审代替真实用户测试。
- 遵循最小必要流程；如果某一步不会改变当前的设计判断，则可跳过。
