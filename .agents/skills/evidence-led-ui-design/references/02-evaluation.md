# 02｜按风险评价：认知走查、连续性、可访问性

检查**设计是否支持具体体验**，而不是把所有维度平均打分。先列出要核查的实际场景：用户想达到什么、从哪里开始、重要对象是什么、成功如何被识别。

## 1. 轻量认知走查（Cognitive Walkthrough）

选一条**关键或不熟悉的操作路径**，从目标使用者所处的知识与情境出发。逐个决策点按 NN/g 的四个问题走查 [R21]：

1. **目标**：用户会认识到此时应尝试这一动作，以实现自己的更大目标吗？
2. **发现**：正确动作的入口是否看得见或找得到？
3. **关联**：用户能理解这个动作（名称、图标、位置）和预期结果之间的联系吗？
4. **反馈**：执行后能看见进展、理解结果，并知道下一步做什么吗？

记录哪个问题在哪一节点可能失败、依据是什么、最小设计修复是什么。**无需**每一个点击都写四条问答；熟悉且无争议的动作可略过。AI 走查只能形成设计风险假设，不能断言用户一定失败。

## 2. 贯穿流程的连续性检查

若涉及多屏幕、Session、文档、任务或跨时段使用，沿实际对象路径检查：

- **归属**：当前内容、编辑、错误、运行状态属于哪个对象？切换后是否会误以为属于新对象？
- **生命期**：开始、进行、完成、失败、中断、回到页面时，用户能解释哪些内容已经保存、哪些还在运行吗？
- **控制**：暂停、取消、撤销、返回和恢复是否有明确入口或后果说明？不存在的能力不应暗示存在。
- **反馈**：进度、部分成功和错误是否持续可见，新的成功是否错误地掩盖旧错误？
- **跨边界**：离开页面/应用再返回后，用户预期和实际状态是否一致？

这是用来捕捉“局部每页都合理，整体却割裂”的专门检查；不意味着所有系统必须支持撤销或自动恢复。

## 3. 基本无障碍要求与扩大测试范围分开

**适用的基本要求不是可选优化。** 对以 WCAG 2.2 A/AA 为目标或负有相应合规要求的 Web 界面，受影响的功能与路径需要检查相关成功标准，包括但不限于：

- **键盘**：2.1.1 Keyboard (A)，交互必须能在适用条件下通过键盘操作；不能仅有鼠标入口。[R23]
- **焦点**：2.4.7 Focus Visible (AA)，键盘焦点可见；2.4.11 Focus Not Obscured (Minimum, AA) 是另一个不同的要求。[R23]
- **控件语义**：4.1.2 Name, Role, Value (A)，确保可访问名称、角色和状态正确；与焦点视觉呈现不是一回事。[R23]
- **必要时适用**：1.4.3 Contrast (Minimum, AA，常规文字至少 4.5:1、大字至少 3:1，存在例外)，1.4.11 Non-text Contrast (AA，适用的 UI 识别信息为 3:1)；2.5.8 Target Size (Minimum, AA，24×24 CSS px 或适用例外)；动态状态提示适用时看 4.1.3 Status Messages (AA)。[R08][R13][R23]

**范围是按改动与风险裁剪，不是删减标准。** 改一个按钮通常检查该按钮、焦点流和受影响任务；跨会话主流程需要检查贯穿操作。若尚未测量或未用辅助技术验证，不得声明“符合 WCAG AA”。原生桌面/游戏等平台应采用适用的平台无障碍要求，不能机械套 Web 条文。

再按真实使用情境扩展：触屏手势、窗口缩放、多语言长内容、慢响应、辅助技术、不同设备、动画敏感性等。不要为普通局部文案调整强制做全站扫描。

## 4. 分清证据性质，才决定修复

| 结论类型 | 足够的依据 | 示例写法 |
|---|---|---|
| **已复现行为故障** | 可复现操作、运行日志/录屏/截图、明确结果 | “切换 B Session 后仍显示 A 的总结，步骤…，已复现” |
| **设计风险** | 认知走查、专业启发式、具体视觉结构与使用情境 | “用户可能把状态图标理解为完成，但尚未做用户观察” |
| **未验证假设/偏好** | 设计提议或待证据支持的偏好 | “更沉浸的反馈或可提升探索感；待用户验证” |

专业设计师判断、AI 审查、静态扫描和用户测试各有用途，不能相互冒充。把**审美偏好**与**可复现问题**分开；不生成无依据的百分比、总分或等级。

## 5. 真实观察与完成条件

条件允许时，让接近目标群体的人**独立执行实际目标**，不先指导操作。观察行为、卡点、恢复、对象误解和视觉反馈的使用，再询问感受；记录环境与样本局限。[R07][R14]

输出只保留影响决定的信息：场景与对象 → 观察/假设 → 影响 → 建议或备选 → 如何复验 → 已验证/未验证。涉及 AI 功能，额外检查能力边界、错误识别、纠错和用户控制，可按需参考 Microsoft HAX [R22]。

未能运行、未能观察真实用户时，明确写 **UNVERIFIED**；纸面 walkthrough 只能检查方法逻辑。
