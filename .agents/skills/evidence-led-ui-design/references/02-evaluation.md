# 02｜轻量 UI/UX 评价与验证方法

这不是万能评分表。根据当前产品和任务选择与决策有关的检查，优先识别实际阻断问题。

## 评价层次：不要混为一谈

| 层次 | 评估对象 | 谁来做 / 方法 | 可以下的结论 | 不能下的结论 |
|---|---|---|---|---|
| 技术可验证 | 交互是否响应、内容是否保存、键盘是否可用、尺寸是否溢出 | 浏览器操作、测试、测量 | 特定条件下通过/失败 | 所有用户都觉得易用 |
| 可用性启发式 | 操作入口是否清晰、反馈是否及时、术语是否符合用户、错误是否可恢复 | 人工或 AI 按启发式审查，标记证据 | 存在值得验证的风险 | 用户实际完成率、统计显著性 |
| 视觉判断 | 排版、层级、节奏、信息密度、品牌适配、整体协调性 | 专业设计师结合产品情境判断 | 有依据的审美/专业评价 | 普适唯一正确的视觉方案 |
| 真实用户研究 | 完成任务时实际发生的行为、困惑、放弃、绕路 | 观察目标用户操作原型/产品 | 本轮参与者真实出现的问题 | 小样本推断全体用户比例 |

## 最小可执行验收

对每个核心用户任务，写清楚：
- 起点、用户意图、触发动作、成功结果。
- 可见反馈：用户如何知道正在进行、已完成、失败。
- 必要的失败/中断路径，以及返回或恢复方式。
- 测试载体（原型/真机/浏览器）、屏幕尺寸和测试条件。

**仅当属于当前任务时**，再加入长文本/多语言、空状态、连续操作、键盘、弱网、窗口缩放、触屏等检查。不需要每次做全覆盖。

## 审查重点

**操作与结构**
- 新用户能否找到主要动作？高频用户是否需要不必要的步骤？
- 主次操作是否清楚，视觉权重是否与操作风险相称？
- 栏目、术语、图标是否能让实际用户理解？
- 状态反馈是否及时且持续；失败之后还能做什么？

**视觉语言**
- 首屏视线首先落在哪里？这是否对应用户当下的任务？
- 标题、正文、次要信息是否形成可读的层级？
- 信息密度与使用时长相称吗？专业工具未必需要大量留白。
- 卡片、边框、阴影、色彩、动效是否帮助分组、提示状态或引导注意？无作用的装饰是否应去除？
- 不同页面是否采用一致但不机械的表达？

**适用的可访问性基线（Web）**
- WCAG 2.2 SC 1.4.3 AA：通常普通文本对比度至少 **4.5:1**，大文本至少 **3:1**；存在明确例外。[R08]
- WCAG 2.2 SC 2.5.8 AA：目标最小 **24×24 CSS px**，但有间距、等效控件等例外；这不是“所有按钮必须 44px”的规则。[R13]
- 另外验证键盘操作、可见焦点、控件语义与错误关联（依实际平台要求）。仅凭截图不能证明符合 WCAG。

## 反馈记录：保持可追溯

每条问题只记录必要字段：

```text
问题：<具体位置和现象>
任务/条件：<用户正在做什么，在哪个状态>
依据：<截图/录像/复现步骤/启发式/专业意见>
类型：已复现的故障 / 设计风险 / 主观偏好
影响：阻断任务 / 误导或高概率失误 / 效率下降 / 低影响
建议：<最小改变与预期效果>
状态：未测试 / 已复现 / 已修复待复验 / 已验证
```

不要用单一“UX 85 分”掩盖差别，更不能把 AI 自评转化为客观性能指标。优先修复阻断任务或造成不可恢复后果的问题。

## 如何做小规模用户验证

- 选实际或近似目标使用者。让他们**独立完成具体任务**，而不是问“你喜欢这个页面吗”。
- 观察在哪里犹豫、绕路、误操作。录制需遵守同意、隐私与组织要求。
- 先记录发生了什么，再解释原因。把受访者的话与 AI 的归因分开。
- NN/g 常把约 5 名参与者作为探索性定性可用性测试的实用起点，但明确说明存在例外；不能借此声称具有统计代表性。[R14]

以上规则需根据实际产品和设计师意见裁剪。参考索引见 [04-sources.md](04-sources.md)。
