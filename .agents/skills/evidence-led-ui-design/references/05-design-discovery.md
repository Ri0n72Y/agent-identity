# 05｜Design Discovery Dialogue：从初始提示词到系统设计简报

> 方法草案 · 2026-10-23。供新系统、重要改版、交互形态不明的任务使用。不是用户研究记录、正式 PRD 或自动填写问卷。依据与适用边界见 [04-sources.md](04-sources.md) R24–R33。

## 为什么需要这一步

委托者通常能说出“要哪些功能”，但不一定能描述系统如何被感知、如何组织对象、用户如何在不同时间与界面间完成目标。直接把功能清单转换成页面会过早锁定产品形态。

本方法结合：NN/g 的**半结构化访谈与漏斗式追问** [R24–R26]、Design Council 的**先发现并定义问题** [R27]、IBM 的**成果意图与回放校准** [R28]，以及 Spec Kit/GSD/Superpowers 等 AI 工作流的**缺口选择、逐步记录和方案确认** [R29–R31]。四者是借鉴，不是某个来源原样提供的完整方案。

**重要界限：** 此处交谈对象可能是产品提出者、开发者或业务负责人，不一定是最终用户。获得的是产品意图与要求，不是目标用户实际行为的证据。不得生成虚构访谈、画像或“验证过”的心理模型。

## 触发、跳过和退出

- **启动**：新系统、重大改版或重要交互形态未定时，先整理已有材料和决策；启动 Discovery 不代表必须多轮问答。
- **追问门槛（三项同时成立）**：① 当前资料不足；② 缺口会改变重要设计方向；③ 无法用低风险、可逆的合理假设继续。否则 AI 应标记假设，主动提出默认方案或原型，不把判断都交还给用户。
- **跳过整轮**：范围明确的文案、按钮、颜色修正；有稳定规范且不存在重要冲突。不要重问现有材料已经回答的问题。
- **退出**：主要体验目标与核心对象清楚；重大冲突已处理或标记待决；AI 能提出可比较的交互方向，其他未知条件不会阻止当前设计。用户也可随时要求“按已有信息继续”；不以大纲填满为目标。
- **简短回放**：新系统/重大改版确认重要意图、硬约束及未决风险，不要求用户逐项批准视觉或技术细节。

## 1. 初始提示词入纲（AI 内部建立，不默认向用户展示空表）

保留**原始用户提示词原文**作为来源。阅读附件、已有实现和已确认决定，先按内容性质归类，**再**把相关内容填入以下“活的大纲”：

- **用户目标**：希望解决的问题与最终结果，不等于指定 UI 结构。
- **明确约束**：必须遵守的布局、平台、功能或其他要求；不能以设计探索为由私自删除。
- **候选方案**：用户或 AI 建议的实现方式，有待比较；不要自动提升为硬约束或最佳设计。
- **观察证据**：已观察到的行为、运行结果与反馈，注明来源；用户转述的行为不伪装成现场观察。
- **开放假设**：尚未验证、可能影响设计的解释、对象关系或行为预期。

每条信息另记**来源和状态**（已确认、推断、待讨论或暂不适用），不要把性质与确认状态混成一个标签。若用户明确要求“左侧放按钮”，先作为需要遵守的要求；若说“比如左侧放按钮”，则是候选方案。若强制程度不明，保留已提出的位置，在替代设计确实会改变它时才确认是否可调整。

| 大纲部分 | 需要了解什么 | 会影响哪些设计选择 |
|---|---|---|
| **产品意图** | 用户最终希望实现什么，现状问题是什么，成功长什么样；有什么非目标 | 是否真的需要该系统、应该优化什么 |
| **目标使用者与情境** | 谁用、在哪里/何时用；分别具备怎样的领域知识、软件熟练度、使用经验 | 初次引导、密度、学习策略 |
| **体验目标** | 效率、控制、安心、协作、探索、成就等何者重要；不希望用户感受到什么 | 视觉/交互反馈取舍 |
| **系统形态** | 主要是工具工作区、连续任务向导、内容浏览器、画布、游戏世界，还是混合；何处开始、如何返回 | 信息架构、主要导航、页面或模式 |
| **核心对象与关系** | 用户实际操作的对象、谁拥有数据、对象之间怎样连接 | 列表、详情、关联、切换与编辑方式 |
| **体验连续性** | 典型的一次使用与多次使用；进行中、离开、切换、恢复、撤销、失败后如何继续 | 跨屏幕/会话/时间的状态与反馈 |
| **核心行为与边界** | 最重要的几条任务路径、例外、权限与危险操作；什么明确不做 | 交互能力、错误路径和范围 |
| **视觉/感官方向** | 想传达的气质，已有品牌、参考界面和反例；触觉、声音、动效是否有作用 | 信息层级、空间、节奏与感知 |
| **已有约束和验证** | 设备/平台、组件系统、时间与技术边界；如何观察是否达到目标 | 实现约束、验证方法及后续风险 |

这是一份**决策索引**，不是九道必答题。单一明确任务可以只有两三项；多角色长期使用的产品则需要扩展重要部分。字段应有来源和状态，不以填充率打分。

## 2. 从大纲生成下一问，而不是按顺序逐项盘问

每一轮：
1. **定位关键缺口并判断能否自主推进**：只有信息不足、缺口影响重要方向、且低风险可逆假设不足以继续这三项同时成立才追问；否则给出依据、默认方向和待验证假设。
2. **确需提问时从完整使用情境问起**：如“从开始会议到会后找回记录，你希望系统怎样陪你完成这一过程？”；避免用具体布局暗示答案。
3. **主动给出设计建议**：当用户无法抽象描述，AI 可以展示不同交互模型及优缺点，说明自己的建议和理由，允许“都不合适”；不必先要求用户选完才做原型。
4. **每轮只解决有影响的决定**，紧密相关问题可合问；每轮更新大纲的事实、约束、方案、假设、已否决理由与待决项，不重复询问，也不设固定轮数。
5. **发现新答案与原目标冲突时**先区分是目标变化还是使用场景补充，再修正理解；不要求用户解决所有低风险实现细节。

**不良问法 → 可执行问法：**
- “要不要现代化三栏 Dashboard？” → “工作进行时，你最需要持续看见哪类信息？不看见什么会影响判断？”
- “喜欢左侧 Sidebar 吗？” → “你是在不同记录间频繁切换，还是长时间专注于当前记录？”
- “主题想用蓝色还是紫色？” → “希望首次使用时给人怎样的感受？有贴近或明确不喜欢的例子吗？”
- “是否要提供撤销？” → “误操作后，用户应如何恢复到预期状态？哪些结果不能撤销？”

用户要求“给我看看再决定”时，可先给粗略的**两种交互模型示意**，而不强迫其抽象回答。不能生成/运行原型时用文字情境或结构草图，明确其未验证。

## 3. 会话中的三种检查点

**发现：** 用户说出真正目标、使用方式或反例，AI 可以纠正问题定义。

**收敛：** 有足够的信息比较最有影响的交互取舍，指出取舍对用户理解、信息密度、视觉反馈、跨状态连续性和实施成本的影响。只有一个合理方案时不人为凑数。

**回放（Playback）：** 用短摘要说明：**用户成果 → 重要约束 → 核心对象和体验 → 推荐的系统形态/交互方向 → 重要待决假设**。让委托者修正重要设计意图，而不是逐一批准全部细节。重大冲突明确保留，其他可逆细节由 AI 自主设计并在原型中验证。委托者确认不代表真实用户认可；之后进入 [SKILL.md](../SKILL.md) 的 Understand / Explore / Materialize / Evaluate。

不把“用户已经确认”扩大为“已通过用户研究”。用户确认的是**委托意图**。

## 4. 示例：一条原始提示词如何变为设计决定（假设场景）

> 原始提示词：“做一个会议录音转写界面，左侧有开始按钮，右边可以看原文和实时总结。”

**初始信息分类（仅示意，并非实际研究）：**
- **用户目标**：会议录音、转写与总结；真正要改善的是跟进、回顾还是两者的连续过程，尚未明确。
- **明确要求**：左侧有录音入口，右侧可查看原文与总结；先保留位置要求，但**不把它宣称为 UX 最优布局**。若用户说明只是举例，再作为可调整方案。
- **候选方案**：进行中工作区或以 Session 为中心的工作区，均未选定。
- **观察证据**：暂无使用记录或实际用户反馈，不得补造。
- **开放假设**：转写、总结、录音及错误如何归属于 Session；跨 Session 切换、恢复的策略。

**先尝试理解完整过程，而非二选一：** “请描述一场会议从开始录音、会中查看内容，到结束后找回记录的使用过程。哪些环节必须顺畅衔接？” 不预设“会中辅助”和“会后检索”只能有一个主目标。

**AI 自主推进：** 假设记录都归属各自 Session，先提出保留当前录音状态提示的低保真工作区供讨论；**录制切换策略仍待决**，若决定会影响重要状态且无法以可逆原型避免风险，再追问。确认前不得把某种切换策略写成生产要求。

**可能的方案对照（待用户讨论）：**
- **进行中工作区**：录音状态始终突出，适合边开会边操作；历史检索要另设入口。
- **Session 工作区**：会议列表和每场记录是主轴，适合跨时间回顾；必须防止当前录制状态随视图切换而被误解。

AI 应说明推荐方向的依据与不确定性；两种工作区可通过原型比较，不能把任何候选方向或 UI 位置宣称为已验证最佳方案。视觉层级与状态反馈需共同设计。

## 5. 纸面反证：不同任务的流程成本

- **按钮小改动**：“保存”改“应用设置”。已有组件与语义足够明确时，不开完整访谈；只核查是否会误导立即生效与保存语义。符合低成本原则。
- **会议系统**：先以完整使用过程确定对象归属与连续性；仅对无法用可逆假设处理的跨 Session 策略追问，将关键决定交给现有 Issue/简报中的最小行为契约。
- **探索型游戏**：“设计元素养成界面”。AI 可以主动提出“配方直接可见”与“反馈驱动发现”两种学习方案及各自风险，围绕探索、理解和掌控感比较；不等待用户回答所有视觉细节，也不只追求操作效率。

这是**纸面方法推演**。它不能证明真实 AI 使用本方法会得到更好的结果。

## 6. 失败模式及修复

- **问卷化**：直接展示全表让用户填 → 只问最大缺口；大纲留在内部，必要时简短展示。
- **越问越细却仍未定义产品**：追问颜色/间距 → 回到最终目标和系统形态。
- **选项诱导**：只给 AI 偏好的布局 → 先开放提问，再给确实不同的选项及“其他”。
- **咨询无止境**：追求字段全部完整 → 三项追问门槛缺一即自主推进；保留未决假设，用原型与结果修正。
- **用户说了算 = UX 已证实**：把产品提出者的回答当研究数据 → 将委托意图和目标用户证据分离。
- **设计已定后不再修正**：材料化/测试出现冲突还坚持简报 → 回到本对话更新真实依据，留下被改变的决定。

## 后续专家审阅重点

请设计师独立评估：大纲是否缺少关键的系统层面问题、提问是否会误导委托者、何时应通过视觉原型代替文字沟通、回放是否足够清楚，以及这套方法会不会对真实设计任务产生过量的谈话成本。专业反馈不是一份新的强制题库。
