# 03｜专业设计师独立审阅邀请（v0.2）

**这是一份未经真实使用验证的 AI 设计方法草案。** 请评价方法，而非为我们直接完成某个 UI 设计。不需要逐条打分或重画产品。

## 第一轮：独立判断（仅看主 Skill）

建议先独立浏览 [SKILL.md](../SKILL.md)，从专业实践直接指出：
- 最可能让 AI 生成**表面合理但整体失败**界面的结构性错误是什么？
- 哪一项重要设计能力仍然缺失？
- 哪一段最可能造成不必要的流程负担或误导？

欢迎否决四阶段框架或 Experience Model 本身。请尽量举一个可想象的反例。**请先独立记录判断，随后再看以下定向问题和文末作者推演，以免被预期答案引导。**

## 第二轮：设计发现对话的定向问题

请按需审查 [05-design-discovery.md](05-design-discovery.md)：它是否真正帮助不了解 UI 设计的委托者表达产品愿景？有无诱导式选项、过早锁定产品形态、把开发者意见假扮成真实用户研究的问题？何时对话已经足够，可以放心停止？不要求按大纲逐项填写；如果结构本身不合理，欢迎直接推翻。

## 其他可选的定向问题

1. **整体体验**：最终目标、对象关系、跨页面/会话/时间连续性与反馈，能否构成实用的最小模型？它遗漏了什么？
2. **设计探索**：什么时候应该挑战功能清单或已有模式？如何判断“真实替代交互模型”与只做几版皮肤？
3. **视觉与交互**：布局、排版、颜色、文案、动效是否被纳入足够早？对于创作工具/游戏是否仍太功利？
4. **评价方法**：四问认知走查和跨对象检查是否可执行？哪些结论不能由 AI、设计师或静态工具声称？
5. **流量成本**：小修、中改、大改的裁剪是否合理？哪条要求实际不会改变设计质量，可以删除？
6. **实验**：后续如何用小成本真人观察或专业盲审检验效果，避免“AI 认为自己更好”的循环论证？

## 第三轮：案例题目（作者结论见文末）

这些案例**不描述任何真实产品的测试结果**。用于判断本方法是否会作出合理决策，也允许设计师提出完全不同的操作模型。

### A｜设置页按钮的小修改

假设：既有设置页的“保存”按钮文字需要改成“应用设置”，操作含义不变。方法应该沿用组件与现有导航，仅核对文案是否准确、操作后的可见反馈、键盘和焦点；**不应**生成三套页面、体验旅程或完整设计系统。若改名改变用户对“立即生效/稍后生效”的理解，则要检查真实的应用时机。

### B｜会议录音 → 转写 → 总结的连续操作

假设：用户开始录音，实时转写，之后查看总结，也会切换会议 Session。请检查：录音归属哪个 Session；切换时录制应继续、暂停还是阻止切换，用户如何得知；旧文本/旧错误是否短暂出现；总结成功是否遮蔽录音/ASR 失败；返回后录制状态、已保存结果和未完成操作如何被解释。可探索“以 Session 为主的工作区”与“以进行中录制为主的工作区”，不只重新排列 Tab。

### C｜探索型游戏界面

假设：玩家逐步发现水与火会产生某种反应，并决定何时收集产物。体验目标可能包括好奇、因果理解、掌控与惊喜，而不只是用最少点击完成收集。请比较直接显示反应配方与通过连续可感知的反馈帮助玩家学习，两种模型怎样处理发现成本、可解释性与挫败风险。对核心事件使用视觉、声音、动效及适用的替代反馈；不要预先假定特定模型更好。

请先形成自己的案例判断，之后才阅读文末的作者内部纸面推演。

## 反馈形式

自由表达即可。最有用的是“问题 → 为什么实际会失败 → 修改建议/反例 → 是否阻断”。如果时间有限，仅指出影响最大的一到三个问题。不要求完成所有问题。

AI 自评、设计师专业评审、技术行为验证和真实用户观察必须分别记录。可追溯来源在 [04-sources.md](04-sources.md)，研究假设见 [01-research.md](01-research.md)，轻量走查见 [02-evaluation.md](02-evaluation.md)。

## 作者内部推演（请在独立审阅后阅读）

以下是作者预期而非正确答案；仅用于检验规则是否可执行，不是设计师共识或真实用户验证。

### 内部纸面推演结果（不是验证）

- A：只需 Understand 的局部语义 + Materialize 的必要变更 + Evaluate 的局部确认。Explore 可以跳过。**注意失败条件**：改名实际改变操作语义。
- B：Experience Model 必须覆盖 Session 和记录/错误归属及持续状态；两个候选交互模型可作结构比较。**注意失败条件**：局部页面都漂亮，但切换后含义不明或失败被遮蔽。
- C：Explore 必须比较学习和反馈策略，不应只按效率取舍；Materialize 至少应表达时间与反应反馈。**注意失败条件**：用 UI 装饰替代玩法中的可感知因果。
