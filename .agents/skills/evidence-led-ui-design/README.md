# AI UI/UX 设计方法：专业审阅包（v0.1）

> 调查日期：2026-10-22。**研究初稿，未获专业设计师审阅，未通过实际项目或用户测试。**

## 目的

针对开发者使用 AI 生成 UI 时容易出现的两个问题：视觉风格雷同、用户任务难以完成。目标不是造出一种“AI 风格”，而是让 AI 能从真实业务出发，提出可解释的方案，并让专业人员与用户检验结果。

## 从哪里读起

1. **先读 `references/03-designer-review.md`**（约 5–10 分钟）：给专业设计师的审阅说明及反馈表。
2. 阅读 `references/01-research.md`：社区观点、研究证据及相互冲突的结论。
3. 阅读 `SKILL.md`：拟交给 AI Agent 执行的短流程。
4. 按需查看 `references/02-evaluation.md`：评价维度和轻量验证方法。
5. `references/04-sources.md`：来源、证据级别、链接与局限。

## 当前判断（不是已证实的实验结论）

- 应将「视觉表现」与「可用性」分开评价。
- 先理解用户要做的任务，再确定信息结构和视觉语言。只凭“现代、美观”等形容词难以支撑具体设计决策。
- 真实 UI 截图、业务数据和操作流程，比代码自我审查更能暴露设计问题。
- AI 的评估是问题假设，不能代替专业审查、无障碍检测或用户测试。
- 通用 Skill 应轻量；项目特定的设计规则应进入项目上下文，而不是固化为所有产品的规则。

## 不做什么

- 不提供“最佳风格”“万能配色”或机械化评分总分。
- 不把特定 SaaS 审美当作所有产品的目标。
- 不强制每个任务都做三套方案、完整访谈或大型设计系统。
- 不宣称已经验证这套 Skill 可以改善生成质量。
- 本包不修改任何现有项目，不包含别人的设计素材或受限许可代码。

## 专业审查后如何迭代

请先指出**实际错误、遗漏、场景不适用和过度流程化**的地方。最好附一个反例或具体任务。仅对经过确认的问题改写 Skill，其他意见可以先放到 reference 的待验证部分。可以用两个真实项目界面做前后对比，再决定是否采用。
