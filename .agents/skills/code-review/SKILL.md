# Code review

独立判断变更是否满足要求，优先发现真实缺陷、边界破坏和不必要的维护成本。审查期间保持只读，除非用户另行要求修复。

## 以可核查的证据建立上下文

确认审查范围、需求和比较基线。读取可访问的差异、相关源码、调用方、已有实现及必要测试。将实现者的说明、测试报告和 CI 结果作为线索，不作为正确性的替代证据；不继承实现者的设计结论。

当差异之外的路径会决定行为时，沿真实的调用、状态和依赖关系检查。无法看到必要代码或验证结果时，明确限定审查结论的范围。

## 审查行为与设计

优先检查需求是否落实，以及变更是否破坏既有契约。根据实际风险追查状态一致性、并发与异步时序、错误及取消路径、权限、资源清理和跨模块影响。测试通过不代表这些路径已经被覆盖。

同时判断代码是否放在正确的职责所有者中，是否遗漏了适用的现有能力，是否增加了无必要的抽象、依赖、兼容层或测试负担。React 的 View/功能组件分离是可选的职责边界；只有当混合职责或强行拆分产生具体问题时才提出修改。不要将个人风格、行数或抽象数量当成缺陷。

## 只报告成立的问题

每条 Finding 必须指出准确位置、可触发的情形、具体影响和最小合理修正；区分本次引入的问题与已存在的问题。对可能性推断标明不确定性，不将未经验证的风险写成事实。不要为凑数量提出意见。

按影响排列问题：`P0` 阻断性严重故障，`P1` 重大正确性/安全性问题，`P2` 明确的一般缺陷或有实际代价的结构问题，`P3` 低影响但值得处理的具体问题。可选建议与必须修复项分开。

输出先列 Findings（位置、触发条件、影响、建议），再简述审查范围及关键验证缺口。没有成立的问题时写 `No findings.`；这只表示已检查范围内未发现可报告问题，不表示未经验证的路径必然正确。
