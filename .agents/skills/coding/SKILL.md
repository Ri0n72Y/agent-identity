# Coding

以现有代码和需求为依据，完成范围最小、职责清晰、可验证的修改。

## 定位正确的修改点

实现前先读取可访问的项目约束、相关实现及调用方；对缺陷追踪实际执行路径，定位共同原因。不要只修复报告中出现的一个症状，也不要为了预防假设中的需求扩大任务。

优先复用现有能力、标准库与已安装依赖。只有现有职责无法合理承载新行为时，才增加新的组件、Hook、接口或依赖。抽象的收益应体现在明确的职责、依赖边界或实际复用上；代码行数和表面重复本身不足以成为拆分依据。

## 保持组件与状态边界

在 React/TSX 中，当展示结构与业务逻辑都具有实质复杂度时，优先考虑同文件双组件：私有 `View` 负责 DOM、样式、局部视觉交互和动画；导出的功能组件负责业务状态、API、业务事件与组合，通过类型明确的 props 注入数据和回调。私有 props 类型无须导出。简单组件不强制拆分。

状态由真正需要协调它的最小范围持有。只有当有独立职责、生命周期或复用需求时，才提取自定义 Hook；纯计算优先用普通函数。不要为压缩组件行数而把无关逻辑塞进一个大 Hook。

在能改善导航或解释隐含职责时，为顶层符号写简短的标准 JSDoc `@summary`；必要时补充 `@param`、`@returns` 的语义，不重复 TypeScript 已表达的类型。源码发生职责变化时同步更新说明。

## 实施与收口

修改只覆盖需求及为正确性必需的关联路径。保留现有接口、错误处理和生命周期约束；不要引入无关重构、预留架构或仅用于通过检查的特殊分支。

修改后核对差异及受影响调用方。按风险执行已有的类型检查、测试或针对性验证；发现缺陷时，优先验证造成缺陷的真实边界。不要为了每次微小修改都新建测试框架或重复运行昂贵检查。

交付时说明实际修改、已执行且通过的验证、仍未验证的部分。没有访问源码、执行命令或观察结果时，不宣称相应工作已经完成。
