# React component coding

对具有实际业务逻辑的 React 组件，优先在同一 JSX/TSX 文件内区分功能入口与私有展示层。让 UI 能通过 props 独立理解和呈现，同时避免为简单组件增加无用层次。

## 分清职责

- **私有 `*View`**：负责 JSX/DOM、样式、视觉布局、hover/展开等局部展示状态和动画（如 `useSpring`）。通过 props 获取显示数据和交互回调，不读取业务 Store，不发起业务 API 请求。
- **对外功能组件**：负责业务 Hook、数据获取、业务状态和操作编排，将数据与回调传给 View。公开接口依照原有组件契约设计，View 与其 props 类型默认不导出。
- 视觉行为与业务行为交叉时，按状态所有者与实际依赖划界；不要机械禁止 View 使用 Hook。

这种拆分用于职责确有区分的组件。纯展示组件和简单组件可以保留单一函数；专属 View 优先留在同文件，只有真实复用或独立维护需要时才拆文件。不要额外制造转发 Hook、包装组件或重复类型定义。

## 保持可读、可索引

顶层具名组件、Hook 和承担独立职责的函数默认使用简短的标准 JSDoc `@summary`，写明职责。局部匿名回调及职责显而易见的简单辅助函数可以省略；`@param`、`@returns` 仅在能补充语义时使用，不重复 TypeScript 类型。代码职责变动时同步修改注释。

私有 props 类型应清楚表达 View 所需的数据和事件。由功能组件负责适配业务数据，避免让 View 感知 API 响应格式或业务实现细节。不为了方便预览而改动生产代码的导出边界；独立预览由外部工具处理。

## 完成条件

修改后沿数据和事件传递路径核对：业务依赖留在功能侧，展示侧可由 props 驱动，视觉行为保持正常；报告未能验证的部分。遵循仓库已有约定与明确需求，不对无关代码施加此风格。
