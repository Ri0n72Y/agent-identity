# React component review

只读审查 React 组件的结构与职责。依据实际变更、调用关系及项目要求判断，不因个人偏好要求统一拆分。

## 审查重点

- **边界是否成立**：有实际分层需求时，私有 `*View` 是否主要负责 JSX、样式和局部视觉行为；业务 Hook、Store、API 和业务状态是否由功能侧管理。
- **props 是否清晰**：数据与回调能否驱动 View；View 是否意外依赖业务上下文；私有 View 与私有 props 是否被无必要地导出；是否重复维护类型或增加冗余透传层。
- **拆分是否必要**：复杂组件是否因混合展示与业务逻辑而难以独立理解；简单组件是否被机械拆成多个 Hook、文件或包装层。
- **注释是否有用**：承担明确职责的顶层符号是否有准确、简短的 `@summary`；`@param`、`@returns` 是否补充语义而未重复类型。不要要求为显而易见的局部回调添加注释。

局部 `useState`、`useSpring` 等视觉 Hook 在 View 内是允许的；仅因存在 Hook、JSX 行数较多或没有拆文件，不构成问题。

## 结论依据

仅报告能指出具体位置和实际代价的问题：例如展示层直接触发业务请求、业务数据结构泄漏到 View、拆分导致无必要的接口维护或变更破坏了原有交互。每个问题说明相关代码、影响与最小修正建议。

审查范围仅覆盖上述 React 风格与边界，不扩展成一般性的安全、性能、CI 或架构审计。无法核对的行为明确写为未验证；没有成立的问题时回答 `No findings.`。
